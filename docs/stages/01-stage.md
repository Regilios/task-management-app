# 01-stage — доменная модель заказов и обращений

StockFlow — учебный портфолио-проект на Java для обработки клиентских обращений и заказов. Первый этап собирает бизнес-сценарий в памяти: история сообщений → обращение → назначение оператора → заказ с сохранённым исходным обращением.

Этап завершён 2026-10-23. Ветка `01-stage` сохраняет его итоговый срез; этот результат перенесён в `main`. Дальнейшая разработка HTTP API ведётся в `02-stage`.

## Реализованные возможности

| Область | Поведение |
| --- | --- |
| Позиция заказа | `Product` хранит код товара и целое количество от 1 до 10 000. Код нормализуется по краям; недопустимые значения отклоняются при создании. |
| Черновик заказа | `Order` позволяет добавлять и удалять позиции, менять итоговое количество. Повторное добавление того же кода суммирует количество с проверкой ограничения модели. |
| Состояния заказа | Начальное состояние — `DRAFT`. Непустой черновик можно подтвердить, черновик можно отменить. Изменение позиций разрешено только в черновике; переходы между `CONFIRMED` и `CANCELLED` запрещены. Повтор достигнутого конечного состояния не меняет заказ. |
| Заказы клиента | `OrderService` создаёт заказы и возвращает выборку одного клиента в порядке создания. Отсутствие заказов даёт пустой список. Результат защищён от изменения состава и содержит прежние объекты заказов. |
| Сообщения | `Message` содержит ID, текст, направление и `Instant`. `MessageListService` сохраняет порядок добавления: повтор ID с теми же данными не создаёт запись, конфликт данных отклоняется. |
| Диалоги и обращения | `Dialog` принадлежит клиенту, хранит историю сообщений и свои `Ticket`. `DialogListService.open` сохраняет активное обращение либо создаёт следующее после закрытия прежнего. История диалога при этом сохраняется. |
| Работа оператора | Обращение проходит состояния `OPEN → ASSIGNED → CLOSED`. Чужое назначение не перезаписывается; закрытие выполняет назначенный оператор. Общая очередь содержит только `OPEN` в порядке создания обращений. |
| Открытые обращения за период | `DialogListService.findOpenTickets(from, to)` отбирает текущие `OPEN` по неизменяемому времени открытия, включая обе границы, и сортирует по времени открытия, затем по ID диалога. |
| Источник заказа | `TicketOrderService` создаёт заказ из обращения или связывает с ним независимый заказ того же клиента. У заказа максимум одно исходное обращение; у обращения может быть несколько заказов. Контракт покрыт восемью сценариями. |

История сообщений и очередь обращений имеют разные роли. Добавление сообщения само по себе не открывает новое обращение: открытие выполняется отдельной командой `DialogListService.open`.

## Организация кода

| Часть | Ответственность |
| --- | --- |
| [`core/model`](../../core/src/main/java/dev/stockflow/core/model) | Объекты предметной области и допустимые изменения их состояния. |
| [`core/service`](../../core/src/main/java/dev/stockflow/core/service) | Коллекции в памяти, поиск и координация операций над моделями. |
| [`core/state`](../../core/src/main/java/dev/stockflow/core/state) | Состояния заказов и обращений, направление сообщений. |
| [`core/src/test`](../../core/src/test/java/dev/stockflow/core) | Проверки моделей и сервисов через JUnit; сервисы создаются напрямую без запуска приложения. |
| [`app`](../../app) | Spring Boot-приложение, конфигурация PostgreSQL, Liquibase и проверки инфраструктуры. |

Код рассчитан на Java 21. Maven-проект состоит из модулей `core` и `app`. В `core` используются аннотации Spring и Lombok, при этом сценарии сервисов проверяются с явным созданием объектов и передачей зависимостей через конструктор.

Владельцы состояния разделены:

- `OrderService` хранит все заказы по `clientId`.
- `DialogListService` хранит диалоги и общий порядок создания обращений.
- Каждый `Dialog` хранит собственные обращения и историю сообщений.
- `TicketOrderService` хранит только связи между существующими `Ticket` и `Order`; получает те же экземпляры двух сервисов через конструктор.

Связи не дублируют заказы и обращения. `findSource` возвращает прежний объект `Ticket`, а `findOrders` — защищённый снимок состава с прежними объектами `Order`. Позднее изменение состояния заказа видно через ранее полученную ссылку, но новые связи не пополняют ранее полученный список.

## Контракт связи заказа с обращением

| Метод `TicketOrderService` | Результат |
| --- | --- |
| `createFromTicket(dialogId, ticketId)` | Находит обращение, получает клиента из его диалога, создаёт новый пустой `DRAFT` через общий `OrderService` и сохраняет источник. Каждый успешный вызов создаёт отдельный заказ. |
| `linkOrder(dialogId, ticketId, order)` | Выбирает источник уже созданному заказу. Повтор той же связи не создаёт дубль; другой клиент или другой уже выбранный источник отклоняются. |
| `findOrders(dialogId, ticketId)` | Возвращает заказы указанного обращения в порядке первой привязки; известное обращение без заказов даёт пустой список. |
| `findSource(order)` | Возвращает конкретный исходный `Ticket`, либо `null` для независимого заказа. |

Обращение адресуется парой `dialogId` и `ticketId`: одинаковые `ticketId` разных диалогов не означают одно обращение. Заказы на этом этапе передаются объектами; отдельного работающего идентификатора для поиска заказа нет. Два пустых заказа одного клиента остаются разными заказами.

Недопустимые аргументы новых операций дают `IllegalArgumentException`, неизвестная цель — `NoSuchElementException`, несовместимая связь — `IllegalStateException`. Проверки выполняются до создания заказа или изменения связи. Закрытие обращения и отмена заказа не удаляют источник. Проверка клиента в этой операции является бизнес-ограничением связи; механизм авторизации пользователей здесь не реализован.

## Контракт выборки открытых обращений за период

`Ticket` хранит время создания в поле `final Instant openedAt`. Назначение и закрытие обращения не меняют это время. Перегрузки конструкторов `Ticket` и `Dialog`, а также `DialogListService.open` и `Dialog.openTicket` принимают явный `Instant`; обычные варианты используют текущее время при создании нового обращения. Повторное открытие уже активного обращения сохраняет его объект и исходное время.

`DialogListService.findOpenTickets(from, to)` читает общую очередь и возвращает обращения, которые на момент вызова находятся в состоянии `OPEN` и открыты в диапазоне `from <= openedAt <= to`. Это выборка текущего состояния по времени открытия; прежнее состояние обращения в прошлом периоде не восстанавливается. Равные границы допустимы. `null` в любой границе и `from > to` дают `IllegalArgumentException`.

Результат упорядочен по `openedAt` по возрастанию, при равном времени — по `dialogId` в естественном порядке строк. Состав списка защищён от изменения и фиксируется при чтении: новые обращения не появляются в прежнем результате. Элементы остаются теми же объектами `Ticket`, поэтому последующее назначение или закрытие видно через ранее полученную ссылку.

| `TestMessage`, `TestMessageList` | Валидация сообщения, повтор ID, конфликты содержимого и порядок истории. |
| `TestTicketDialog`, `TestTicketOperatorValidation` | Открытие, назначение, закрытие, очередь, сохранение истории, области ID и защита результатов чтения. В `TestTicketDialog` добавлены семь сценариев периода: текущие статусы, включительные и равные границы, порядок при одинаковом времени, пустой результат, недопустимые границы, неизменность времени открытия и снимок с прежними объектами обращений. |
| `TestTicketOrderServices` | Восемь сценариев: создание заказа и сохранение источника, повтор связи без дубля, два разных заказа одного обращения, отказ для другого клиента, запрет смены источника и разделение областей ID, неизвестные цели, недопустимые аргументы, снимок состава с прежними объектами заказов. |

Доменные сценарии первого этапа реализованы и проверены. Локальный запуск `core` от 2026-10-23 завершился успешно: 135 выполнений, 0 failures/errors/skipped. Проверки относятся к последовательному выполнению операций с данными в памяти.

Запуск тестов бизнес-модуля без Docker:

```powershell
.\mvnw.cmd -B -ntp -pl core test
```

Отдельный инфраструктурный набор [`InfrastructureIT`](../../app/src/test/java/dev/stockflow/InfrastructureIT.java) использует Testcontainers и настоящий HTTP-сервер на случайном порту. Он проверяет подключение к PostgreSQL, применение стартовой миграции, повторный запуск Liquibase без повторного изменения схемы и readiness приложения.

Полная проверка с доступным Docker:

```powershell
.\mvnw.cmd -B -ntp -Pintegration verify
```

Обычный `test` и интеграционный `verify` подтверждают разные части системы. На 2026-10-23 локальный Docker Engine недоступен; интеграционный `verify` при завершении этапа локально не запускался. Статус CI следует проверять по конкретному запуску GitHub Actions.

## Границы текущего этапа

- Бизнес-данные находятся в памяти одного процесса. Перезапуск теряет заказы, диалоги и связи; PostgreSQL пока содержит только инфраструктурный маркер Liquibase.
- Сервисы не обеспечивают согласованность параллельных команд; проверки выполняются для последовательного использования.
- Бизнес-операции пока не опубликованы через HTTP API. Внешние мессенджеры, пользовательский интерфейс и аутентификация не подключены.
- Складские остатки, резервирование, цены и отгрузка не реализованы. `Product` в этом срезе представляет позицию заказа с кодом и количеством.
- Демонстрируются локальные сценарии портфолио-проекта. Данных о production-эксплуатации, нагрузке или отказоустойчивости нескольких экземпляров приложения нет.
